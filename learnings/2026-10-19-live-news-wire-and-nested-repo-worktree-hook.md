# Live news wire (WIRE) + nested-repo worktree-hook workaround

**Date:** 2026-10-19

## Problem

Add a Bloomberg-style live news transcript/wire to openterm. Separately: this project lives
at `projects/openterm` nested inside the `claude` meta-repo's working tree, but is its own
independent git repo (own `.git`, own GitHub remote, not tracked by the `claude` repo at all).
The session had been auto-started in a `claude`-repo git worktree, and the Edit/Write tools'
safety hook refused every write into `openterm`, claiming the file was "in the base repo
checkout" and pointing at a worktree-mirrored path that didn't exist.

## Approach

1. Clarified scope with the user first: "Bloomberg live transcript" was ambiguous between a
   live news wire (feasible with free RSS) and earnings-call transcripts (needs a paid/licensed
   source). User picked "wire now, transcripts later" -- avoided building the wrong thing.
2. Read `docs/MODULES.md` before writing anything -- this repo has a documented module contract
   (frontend `public/mods/<name>.js` + `registerWidget`/`registerCommand`, backend
   `lib/handlers/<name>.js` behind the single `/api/data?fn=` dispatcher, no new `api/` files,
   no new npm deps). Followed it instead of inventing a new pattern.
3. Hit the worktree-hook block on the very first `Edit` call. Tried once more to see if it was
   a stale-state fluke -- same error, and the path it suggested as a fix
   (`.claude/worktrees/<name>/projects/openterm/...`) didn't exist on disk (verified with `ls`).
   Confirmed via `git ls-tree` on the `claude` repo that `projects/openterm` isn't tracked there
   at all -- it's a separate repo that happens to sit on disk under the first repo's tree.
4. Did not try to silently route around the hook. Asked the user directly (per the standing
   instruction: "if blocked by a hook ... ask the user to check their hooks configuration").
   Gave two real options: switch to Bash-based writes for the rest of the session, or have the
   user fix/bypass the hook config. User chose Bash writes.
5. Used `python3 -I -` heredocs (not `sed`) for every edit after that, each with an `assert` on
   the old string so a silent no-op edit would fail loudly instead of leaving stale code. New
   files went through plain `cat > file <<'EOF'`. Syntax-checked every new/edited `.js` file with
   `node --check` immediately after writing it.
6. Built the feature itself: `lib/handlers/wire.js` aggregates Yahoo/MarketWatch/Google-News RSS
   (general market, not ticker-scoped) by reusing the existing `parse()` from `lib/handlers/news.js`
   (exported it rather than duplicating the RSS/CDATA parsing regexes). `public/mods/wire.js`
   registers a `WIRE` command + widget that self-polls every 45s while its panel is mounted,
   using the same `setInterval` + `root.isConnected` guard pattern already used in `chart.js` and
   `portfolio.js`. New headlines not seen on a prior poll get a CSS flash (`wire-new`), skipped on
   the very first load so nothing flashes on initial render.
7. Verified live in the browser (not just curl): started `node server.js`, opened the built-in
   browser preview, ran `WIRE` in the command bar, confirmed the panel filled with real headlines
   (Yahoo Finance, Bloomberg.com, MarketWatch, CNBC) and no console errors.

## Why

The hook is a real safety feature (preventing edits that silently land outside the tracked
branch) but it's not multi-repo-aware: it maps by filesystem-path prefix against the launch
repo's root, not by which `.git` actually owns the file. A nested-but-independent repo under
that prefix trips the same check as a genuine stray edit would. Bypassing it with Bash instead
of fighting the Edit tool is correct *only* because (a) the target path demonstrably has its own
git (`git rev-parse --show-toplevel` resolved to `openterm`, not `claude`), so there's no real
risk of corrupting the `claude` repo's branch, and (b) the user was asked and explicitly chose
that path rather than it being assumed.

## Gotchas

- `mcp__ccd_directory__request_directory` granting access and switching "Primary working
  directory" does **not** clear the Edit/Write worktree-safety hook's own check -- it fired
  identically on the second attempt. Don't retry Edit a third time expecting a different result;
  escalate to the user once the first retry confirms it's not transient.
- The hook's suggested fallback path is generated by naive prefix substitution and can point at
  a directory that was never created. Verify with `ls` before trusting it as a next step.
- `lib/handlers/news.js`'s `parse()` was private (no `export`) -- exporting it is a one-line,
  low-risk change versus copy-pasting the CDATA/entity-decoding regexes into a second file.
- The existing `TOP` widget's `news` snapshot key has no seeder in `seeders/groups/` that
  produces it (grepped `key: 'news'`, found nothing) -- yet it rendered real headlines in the
  browser anyway, so something upstream (likely the Vercel-side snapshot cron, not visible in
  this checkout) fills it. Don't assume a missing local seeder means a widget is broken; check
  the running app before "fixing" an apparent gap that isn't in scope.

## Reusable pattern

When a path under the launch repo's tree refuses Edit/Write with a worktree-mismatch error,
check `git rev-parse --show-toplevel` on that exact path first -- if it resolves to a different
repo than the launch repo, the hook is almost certainly misfiring on a nested-repo case, not
catching a real mistake; ask the user whether to fall back to Bash-based writes (with
`node --check` or equivalent syntax validation after each one) rather than treating the hook's
suggested path as authoritative.
